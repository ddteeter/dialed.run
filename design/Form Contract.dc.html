00 / Two failures

Four lanes shipped one look for two different events. That is the bug.

FIELD FAILURE

The form is intact. The fix is inside it.

  • Cause: a zod issue on one or more fields
  • Marked at the fields, in yellow
  • Recovery: edit, submit again
FORM FAILURE

Nothing was saved. The fix is not inside it.

  • Cause: network died, 500, expired session
  • Marked at the button, outlined. Never yellow
  • Recovery: Try again, same values

No field is ever marked for a 500. Yellow means “the fix is here” — spending it on a server fault teaches runners to distrust it.

01 / Where it renders

Per-field or summary is settled by count, so every lane lands in the same place.

1 FIELD ERROR

Field message only. No summary. Focus moves to that field.

2+ FIELD ERRORS

Summary at the top and every field message. Focus moves to the summary.

FORM FAILURE

Band above the button. No summary, no field marks. Focus moves to Try again.

The screen-reader path — the part every lane missed

Every form mounts exactly one role="status" region, permanently. It is empty until a submit resolves, then it takes one sentence, on every outcome. Then focus moves. Announce, then move — never move without announcing.

ONE FIELD Nothing saved. One field needs a fix.
N FIELDS Nothing saved. Three fields need a fix.
FORM FAILURE Nothing saved. Your connection dropped.
SUCCESS Run logged.

Field messages are not live regions — they are wired with aria-describedby and the input carries aria-invalid. Two regions firing at once means one is lost.

02 / Field error anatomy

Marked, not reddened. The signal is border weight plus a yellow band — never hue alone.

PAPER SURFACE
Half-zip

Half-zip

THE MARK

Border goes 1px rule → 2px ink (2px paper on dark). Padding drops 1px so the box never resizes. Value is never cleared or reformatted.

THE MOTION

None. The doctrine already ruled: offline / error — nothing, deliberately static. No fade, no height transition, and no shake. A shake is a spring in costume.

THE CLEAR

On input, not on blur, with no re-validation. Nothing stays marked while you are fixing it. The next submit is the next verdict.

PINK IS NOT FAILURE

#FF2D8A is action. It never marks an error. Yellow #F5FF3D is the only failure fill in the product.

03 / Two blocks

Both open with the same two words. Everything after them differs.

SUMMARY — TOP OF FORM, 2+ ERRORS
Nothing saved Three fields need a fix.
Temperature — Pick a temperature between -40 and 140. Distance — Enter a distance in miles. Verdict — Say whether this outfit was useful.

Rows are buttons that focus their field — not anchors. A form is not a document. The block itself takes focus on landing.

FAILURE BAND — ABOVE THE BUTTON
Nothing saved Your connection dropped. Try again

Sits where the eyes already are. No fill, no yellow, values untouched. Never a toast — a toast takes the retry with it when it leaves.

NETWORK

Your connection dropped.

500

Our end failed. Nothing about your run changed.

SESSION EXPIRED

The one case that leaves the screen: route to sign-in carrying the payload, return to the filled form.

04 / Submitting

Not disabled. Not resized. Brackets breathe and the verb keeps going.

IDLE
Log run
PENDING
[Logging]
RULES
  • Never the disabled attribute. Disabled buttons drop focus and stop announcing. Use aria-disabled + aria-busy and a re-entry guard in the handler.
  • Both labels share one grid cell, so width never jumps.
  • Inputs go readOnly while in flight, never disabled.
  • No spinner. The breathing brackets are the product's one waiting device.
  • On success the button returns to idle and the screen moves on. No green check, no success toast.

05 / One schema, run twice

Client pre-validation exists. It cannot drift, because there is only one schema.

Rules live in one module under src/lib/schemas/ that imports nothing from the server. The server function uses it as its gate; the form imports the same object for a pre-check. Error copy lives in the schema's message, so the sentence and the rule are the same edit.

// src/lib/schemas/log-run.ts — the only place these rules exist
export const logRun = z.object({
  tempF: z.number().min(-40).max(140, {
    message: 'Pick a temperature between -40 and 140.' }),
  verdict: z.enum(['useful', 'too warm', 'too cold'], {
    message: 'Say whether this outfit was useful.' }),
});
// the form — courtesy pre-check, on submit only
const { submit, pending, fieldErrors, failure } =
  useFormSubmit({ schema: logRun, action: logRunAction });
WHEN IT RUNS

On submit only. Not on keystroke, not on blur. It saves a round trip; it is not a live critic.

A HAND-WRITTEN RULE IS A BUG

No if (!x.includes('@')) in a component, ever. Components never author error strings.

SERVER-ONLY RULES

Name uniqueness, ownership, session, rate limits. They surface through the same field path — the user cannot tell which side answered.

THE GATE IS THE SERVER

It always runs. The pre-check is a courtesy and is allowed to be wrong; the ZodError from the boundary is the authority.

The primitive

src/ui/FormField.tsx ships the whole contract: useFormSubmit, FormField, FormStatus, FormErrorSummary, FormFailureBand, SubmitButton. A form built on them cannot get this wrong. A form that hand-rolls any of them is a review failure.
